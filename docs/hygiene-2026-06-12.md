## FIX 1 - SEC-4 verdict-shape gate (api/validate-key.js) - FIXED `5b752b4`

Port of Grow `3264c1a` / Vertica `6d30289`.

### Root cause (traced)

Homestead's R2-H1 (`344b808`) gates key on `status !== 200`: a NON-200 without
a business error is routed to 502. But an LS HTTP **200** whose body parses to
`{}` (or shape-drifts: no boolean `valid`, no `license_key` object, no `error`)
passed every gate and fell through to a fabricated definitive verdict at two
sites:

1. **Pre-/activate store-compare leg** (fresh activation path): empty
   `preCheck.json` -> `preMeta = {}` -> `String(undefined) !== expectedStoreId`
   -> definitive 200 `"This licence key is for a different product."`
2. **Main leg** (validate-with-instance AND post-activate): empty `js` ->
   `lk = {}` -> `status = null` -> `isActive = false` -> definitive 200
   `"This licence key is not active."`

The C1-hardened client (`validateKeyRemote` + paywall mount effect) trusts our
HTTP-200 boolean verdicts and wipes `hhp_key`/`hhp_instance` on them. An LS
maintenance page or CDN/WAF intercept served as 200 JSON would de-license
paying customers at mount-revalidate; each re-paste then burns one of the 3 LS
activation slots.

### Fix

Shape gate at BOTH sites interpreting an LS 200 body, placed after the
business-error bail on each leg:

```js
if (typeof js.valid !== "boolean" && !js.license_key) {
  return res.status(502).json({ valid: false, error: "Licence server returned an unexpected response. Try again." });
}
```

(pre-check site additionally guards `!preCheck.json`.)

### Approved-rules verification

- (a) Genuine LS business errors on non-200 stay DEFINITIVE: the R2-H1 gate
  passes non-200 bodies WITH `.error` through to the error bail, which returns
  the definitive 200 shape. Unchanged.
- (b) Legit 200 `{valid:false}` without error stays DEFINITIVE: boolean
  `valid` satisfies the gate; the body flows to `isActive` as before. The
  `/activate` success shape (`activated` boolean, no `valid`) passes via the
  `license_key` disjunct.
- (c) Per-licence L6 bump on the ambiguous path: Homestead's L6 limiter is a
  PRE-FLIGHT `incr` (line ~163) that fires uniformly before the LS call on
  every request, valid and invalid alike. It is not a verdict-conditional
  penalty bump (the Grow architecture where this rule originated), so the
  ambiguous path adds no extra bump by construction. Making the pre-flight
  conditional on outcome would defeat its anti-probe purpose (it must count
  attempts, not verdicts). Rule holds structurally.
- Client treats the 502 as transient: CONFIRMED. `validateKeyRemote` (App.jsx
  ~646) returns `{ valid:false, transient:true }` for every non-200 except the
  own-server 400 leg; the mount effect (~7297) keeps stored key + instance on
  `transient`. The malformed-body guard (~625) independently flags transient
  if our own 502 body were ever mangled.

## FIX 2 - CR-1 guarded unlock persists (src/App.jsx) - DISPUTED

The bug class (bare `localStorage.setItem` on unlock legs, where a
private-mode/quota throw kills the unlock after the LS slot is consumed) does
NOT reproduce. Homestead funnels all persistence through `persistState(key,
data)` (App.jsx 557-572), which wraps `setItem` in try/catch, logs
message+code, and returns false on failure. A storage throw can never
propagate into an unlock leg.

### setItem classification table

Every `localStorage.setItem` in the client (repo-wide grep, 2 sites total):

| Line | Site | Path | Guarded? | How |
|------|------|------|----------|-----|
| 559 | `persistState` body | every wrapper call | YES | enclosing try/catch inside the wrapper |
| 7361 | `LS_PENDING` write in LS `Checkout.Success` eventHandler | grace-window open (live code since GATE-1 `85a3f3c`) | YES | inline `try { ... } catch { /* noop */ }` |

Unlock-path legs, all routed through the wrapper or inline-guarded:

| Leg | Lines | Persist call(s) | Unlock state reachable on storage throw? |
|-----|-------|-----------------|------------------------------------------|
| `commitPaid` (URL `?key=` leg 7260 + stored-key revalidate leg 7286) | 7227-7233 | `persistState(LS_KEY)`, `persistState(LS_INSTANCE)`, `clearLS(LS_PENDING)` | YES - persists are guarded, `setPaid(true)` + `setValidating(false)` always run |
| Checkout.Success grace open | 7357-7364 | inline-guarded `setItem(LS_PENDING)` | YES - `setPaid(true)` + `setValidating(false)` follow the guarded write |
| Manual key entry `activateKey` | 7414-7421 | `persistState(LS_KEY)`, `persistState(LS_INSTANCE)`, `clearLS(LS_PENDING)` | YES - `setPaid(true)` follows guarded persists |
| Grace-panel `saveGraceKey` stored-key revalidate | 3949-3958 | `persistState(LS_INSTANCE)`, `clearLS(LS_PENDING)` | YES - `setLicenceKeyMissing(false)` follows guarded persists |

Ordering note: the Grow/Vertica reference pattern sets React state BEFORE the
guarded persist; Homestead persists (guarded) first, then sets state. Because
`persistState`/`clearLS` swallow internally and return a boolean, the two
orderings are functionally equivalent for the CR-1 property ("a storage
failure costs persistence only, never the unlock"). No change made - reordering
would be churn on a live paid product with no behavioural delta.

## FIX 3 - generate.js verdict-consistency - FIXED `5e62d1a`

### Root cause (traced)

`validateLicence` collapsed every non-ok outcome into `{ ok:false, reason }`,
and the handler mapped ALL of them to a single definitive
`401 "Your licence couldn't be verified. Please re-enter your key on the home
page."` Three of those outcomes are ambiguous upstream states, not verdicts:

- `ls.status >= 500` (incl. the 8 s timeout mapped to 504) -> `ls_unreachable`
- non-200 without a business error (WAF/edge intercept, JSON:API `errors[]`
  shape) -> fell through `js.error` to `isActive` false -> `licence_inactive`
- HTTP 200 with a non-verdict body (`{}` from an unparseable 200, shape
  drift) -> same `licence_inactive` fallthrough

Consequence was a single rejected generation with misleading "re-enter your
key" copy (no wipe - the client only `setError`s on non-OK generate
responses), so this is consistency-only, severity below FIX 1.

### Fix

Same two gate classes as validate-key.js R2-H1 + SEC-4, returning
`{ ok:false, reason, transient:true }` (new reasons `ls_ambiguous_status`,
`ls_no_verdict`; `ls_unreachable` now also flagged transient). Handler branches
on `transient` -> `503 "The licence server is temporarily unavailable. Please
try again in a moment."` Definitive rejections (`ls_api_error`,
`licence_inactive`, `store_mismatch`, `instance_missing`, `bad_key_shape`)
keep the opaque 401 untouched. `validation_exception` (the defensive outer
catch; nothing inside the try throws in practice - callLs never throws, redis
calls are individually guarded) stays 401, out of approved scope.

Status code is 503 (not 502) so Vercel logs distinguish licence-leg failures
from the existing Anthropic-leg 502s in the same handler. The split leaks no
per-key gate information: transient fires for all keys alike during an LS
incident, and `reason` still never reaches the response body.

### Cache-semantics note (CRITICAL constraint verification)

The Upstash 1h licence cache (`hhp:lk:ok:<hash>`) was already
positive-only: the sole `redis.set(cacheKey, ...)` runs after EVERY gate
(error, isActive, store_id) has passed, and negative verdicts were never
cached. Both new ambiguous gates return BEFORE that write, so ambiguous
results cannot poison the cache by construction; no cache code was touched.
The canonical instance-binding block (SET NX first-bind + sliding-TTL
refresh) sits in the same success-only section and is equally unreached on
ambiguous paths - semantics untouched as required. Fail-closed property
preserved: every ambiguous path still refuses generation.

### Endpoint status map after fix

| Condition | Status | Retryable? |
|-----------|--------|------------|
| Origin reject / method | 403 / 405 | no |
| Per-IP or per-licence rate limit | 429 | yes (window) |
| Missing/short key, no instance binding, definitive LS rejection, store mismatch | 401 | no (re-enter key) |
| LS 5xx/timeout, LS ambiguous non-200, LS 200 non-verdict body | 503 | yes (new) |
| Anthropic-leg failures | 502 | yes (pre-existing) |
